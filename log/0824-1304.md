# 第四轮阶段记录：改为直接使用 Kitty operator kernel

时间：2026-08-24 13:04（Asia/Shanghai）

## 上一步概述

上一阶段完成了 DartKV 的 Kitty 生命周期、Random selection、K/V page 对齐和 Qwen3 fused
adapter，但同协议 batch1/8 A/B 显示 Dart 通用 fused 路径仍只有官方 Kitty 的约 0.5×/0.39×
吞吐。用户明确要求直接搬运 Kitty 的 operator/kernel，而不是继续用语义相近的 generic
参考 kernel；本阶段停止 profiler，切换实现方向。

## 本阶段完成内容

1. 新增 `src/dart/kitty_kernels.py` 作为统一 native operator facade，直接暴露 Kitty MIT
   Triton 的 `quantize_pack_k`、`quantize_pack_v`、`qk_kernel`、`sv_kernel`、
   `kitty_attention_forward`、`KVCache_Layer` 和 `KittyCache`；缺少 editable import 时自动指向
   `reference/code/Kitty/src`；
2. `examples/benchmark_kitty.py` 的 `kitty-engine` cache 改由 `dart.kitty_kernels` 入口获取，
   不再在 benchmark 内部散落直接 import；
3. 保留 `dart-engine` 作为 Dart 自己的 Qwen3 packed adapter，和官方 Kitty native operator
   路径明确分开，避免把两种 kernel 的吞吐混成一条曲线；
4. 8B 同协议 A/B（prompt100、max_seq_len256、warmup1/repeat1）已记录：
   - 官方 Kitty batch1：14.52 generated tok/s；
   - Dart fused batch1：7.33 generated tok/s；
   - 首 32 output token IDs 一致；Dart packed storage 23.80 MB；
   - batch8：官方 Kitty 135.53、Dart fused 52.44 generated tok/s；
5. 全量测试 46 passed，`pip check` clean；direct Kitty operator facade import/符号检查通过。

## 当前判断

现在系统 benchmark 的 Kitty 路径直接调用 Kitty 原生 page allocator 和 Triton operator；Dart
路径仍保留为实现对照。官方 Kitty 的 Figure 5 数字可以作为论文复现结果，Dart fused 数字必须
单列，直到完成同等 kernel 搬运。当前 8B A/B 的差距证实不能仅通过 Python cache lifecycle
声称达到 Kitty 加速比。

## 下一步工作安排

1. 逐项搬运/适配 Kitty `KVCache_Layer` 的静态 page storage 到 Dart native cache，优先复用
   `quantize_pack_k/v` 的 page layout 和 `PageTable_K/V`；
2. 让 Qwen3 Dart adapter 直接调用 Kitty `qk_kernel/sv_kernel` 的输入布局，减少现有
   `fused_dart_attention` 的多次 Python kernel launch；
3. 用 Qwen3-8B max_seq_len256/batch1/8 重新做 correctness 与 A/B，目标先达到官方 Kitty
   kernel 的同量级，再恢复 8192 Figure 5 sweep；
4. 所有正式结果继续区分 `kitty-engine`（原生 Kitty）和 `dart-engine`（搬运后的实现），
   不使用早期 generic kernel 诊断点验收论文；
5. GPU1 的 GSM8K/Table 3 长任务在 operator 对齐完成后再启动，避免消耗算力跑错误实现。
