## 设计判断

### 为什么先做 page kernel，而不是马上改 Qwen3

当前 `DartHFCache.update()` 遵循 Transformers 公共 Cache 接口，返回的是 dense
K/V；Qwen3 的标准 eager/SDPA attention 没有接收 packed page 和 page metadata 的
入口。直接修改模型 attention 会同时引入模型层、RoPE、GQA、cache position、
beam reorder 和 kernel 正确性等多类变量，难以判断错误来自哪一层。因此本次先把
“一个 packed page 对一个 query token 的 attention 更新”独立出来，继续用
`DartKVCache.get()` 产生的量化 dense cache 作为数值 oracle。

### kernel 的状态与数学路径

每一个 query head 在跨 page 时维护三项 float32 状态：

- `m`：到当前 page 为止的最大 logit；
- `l`：以 `m` 为中心的 softmax 指数和；
- `o`：以相同指数权重累积的 value 向量。

对一个 page 计算 logits `z` 后，更新为：

```text
m_new = max(m_old, max(z))
alpha = exp(m_old - m_new)
w = exp(z - m_new)
l_new = alpha * l_old + sum(w)
o_new = alpha * o_old + sum(w[..., None] * V_page)
```

最后输出 `o / l`。这样 page kernel 不需要保存完整 logits，也不需要把多个
page 拼接成 dense K/V。`m=-inf, l=0, o=0` 作为第一个 page 前的状态，能够统一
处理 sink、量化 page 和 pending page。

### 支持的 page 存储模式

新增 `src/dart/fused_attention.py` 中的 `_fused_page_kernel`，通过 constexpr
分支支持：

| key mode | value mode | 用途 |
| --- | --- | --- |
| dense tensor | dense tensor | sink token 与 pending partial page |
| uniform token-axis packed key | uniform head-dim packed value | uniform K/V 对照 |
| mixed low-2-bit/high-2-bit key | uniform packed value | Dart mixed key 路径 |

key 的 packed layout 直接读取 `[B,H,D,G,P]`、scale/min 和 token-axis bit offset；
mixed key 另外在 page 内读取 channel index，并只对 promoted channel 读取 high
2-bit。value 直接读取 `[B,H,T,P]` 和按 token/head-dim group 的 metadata。所有
指针都使用 tensor element stride，和 `docs/PAGE_LAYOUT.md` 的约定一致。

### wrapper 与 kernel 的边界

`fused_dart_attention(query, cache, fallback=True)` 目前只接受一个 query token，
形状为 `[B,Hq,1,D]`。wrapper 做以下工作：

1. 从 `cache.shape` 检查 batch、KV head、head dimension 和 GQA 整除关系；
2. 建立 `[B,Hq]` 的 `m/l` 和 `[B,Hq,D]` 的累积输出；
3. 通过 `cache.iter_segments()` 按序遍历 sink、量化 page 和 pending page；
4. 根据 segment 类型选择 dense、uniform 或 mixed kernel 分支；
5. 复用同一 state tensor 发射下一 page，最终归一化并恢复 query dtype。

它不会调用 `cache.get()`，不会保存第二份完整 FP16 K/V。当前仍由 Python 遍历
page，因此这不是最终 page-table fused kernel，而是后续 kernel 的单 page 真值。
CPU、非 CUDA、非单 token 或 Triton 不可用时，默认回退到已有的
`streamed_dart_attention`；传 `fallback=False` 则直接报错，适合测试是否误走
fallback。

## 本次代码修改

### `src/dart/fused_attention.py`

- 增加可选 Triton import，不影响无 Triton 的 CPU 安装；
- 增加单一 page kernel，使用 `KEY_MODE`/`VALUE_MODE` constexpr 分支避免为 dense、
  uniform、mixed 各复制一套 Python API；
- 使用 `BLOCK_T=next_power_of_two(page_tokens)` 和
  `BLOCK_D=next_power_of_two(head_dim)`，对不足 block 的 token/channel 做 mask；
- 支持 `B>1` 和 GQA，query head 通过连续分组映射到 KV head；
- 将每 page 的状态保存在 float32，减少 BF16/FP16 page 间累积误差；
- 暴露 `fused_dart_attention`，并在 `src/dart/__init__.py` 导出。

### `examples/profile_reference.py`

profile 现在同时报告四条路径：

1. quantize + pack；
2. 独立 segment dequantization；
3. 完整 materialize + dense attention；
4. Python page streaming 与 Triton fused page attention。

新增字段包括 `fused_page_attention_ms`、
`fused_page_attention_backend`、`fused_page_attention_peak_bytes`、fused 对
量化 dense 的 max abs/RMSE，以及两个 trace 路径。启用 `--trace` 时，会分别写出
`dart_attention_*.json` 和 `dart_fused_attention_*.json`，可以直接在 Chrome trace
中对比 Python loop、Triton launch、unpack 和状态更新。

### 测试

新增 `tests/test_fused_attention.py`：

- CPU 测试确认默认 fallback 与 PyTorch streaming reference 一致；
- CUDA 测试构造 3 个 sink token、2 个 full mixed page、2 个 pending token，使用
  4 query heads 对 2 KV heads 的 GQA；
- 先用 `cache.get()` 生成 expected，再把 `cache.get` 替换为抛错函数，证明 fused
  路径只读取 `shape` 和 `iter_segments`；
- 既有 Triton 解包测试继续覆盖 uniform 2/4/8-bit、mixed promotion、无 promoted
  channel 和 CPU fallback。

### A100 长上下文 profile

命令：

```bash
conda activate dartkv
python examples/profile_reference.py \
  --device cuda:0 --tokens 1024 --page-size 128 \
  --key-group-size 128 --value-group-size 64 --sink-tokens 32 \
  --kv-heads 8 --query-heads 32 --head-dim 128 \
  --promote-ratio 0.25 --repeats 3 --output results/profile-fused
```

固定 seed 为 `20260823`，逻辑形状为 `[B,Hkv,T,D]=[1,8,1024,128]`，query 为
`[1,32,1,128]`。下面的 latency 是三次重复平均值，quantize 是一次 cache
update；peak 是 `torch.cuda.max_memory_allocated()` 在对应阶段重置后的结果：

| 项目 | 结果 |
| --- | ---: |
| quantize + pack | 235.68 ms |
| Triton segment unpack + dequantize | 1.092 ms |
| complete materialize | 3.467 ms |
| dense attention | 0.160 ms |
| Python page streaming | 138.21 ms |
| Triton fused page attention | 1.789 ms |
| Python streaming peak | 35,535,360 bytes |
| fused page peak | 34,951,168 bytes |
| dense attention peak | 51,964,928 bytes |
| fused max abs/RMSE vs quantized dense | `1.53e-4` / `3.31e-5` |
| quantized dense max abs/RMSE vs original | `0.1151` / `0.03225` |
| Dart packed / dense storage | `1,133,568 / 4,194,304 bytes`（3.70×） |

在这个配置上 fused page 比 Python streaming 约快 `77.2×`，但仍比 dense attention
慢约 `11.2×`。这两个数字的含义不同：前者证明把解包和 attention 状态更新放进
page kernel 能消除大量 Python/head 级 launch；后者说明 page wrapper、每 page
launch、非最优的矩阵访问和缺少 page-table/batch 融合仍是主要瓶颈。不能把它们
解释为 Qwen3 端到端速度提升。

## 问题判断

### 已经解决的问题

1. packed page 的 token 顺序现在有显式 metadata 和 stride 描述；
2. 多 page update 不再产生跨 page 的 scale/min 或混合 page；
3. uniform/mixed key 和 value 的 bit unpack 都有 Triton 对照；
4. 单 token page attention 不再需要生成每 page 的 dense K/V 临时张量；
5. online softmax state 可跨 sink、full page、pending page 连续更新；
6. CPU fallback、GPU kernel、GQA、batch 和多 dtype 均有直接证据。

### 尚未解决的问题

1. 每 page 仍由 Python wrapper 发射一次 kernel，page table 还没有进 Triton；
2. 一个 kernel program 仍使用简单的逐元素乘加，没有使用专门的 tensor-core
   QK/SV tile 或 warp-level reduction；
3. 只支持单 query token；`query_tokens>1` 会 fallback 到 Python reference；
4. 没有把 fused path 接入 Qwen3 的 model attention，Transformers Cache API 仍然
   要求返回 dense K/V；
5. 没有测试 batch/beam reorder 后的 packed page 原地重排，也没有生产级 page
   allocator、跨请求复用和多卡调度。

## 本次用户确认后的修订工作安排

根据 Kitty 的静态 page allocator、`PageTable_K/PageTable_V`、sink buffer、
Q-buffer、local value buffer 和 attention kernel 的组织方式，后续第四阶段按以下
可验收里程碑推进。每个里程碑都必须保留 Dart 的 PyTorch segment 作为真值，不把
“kernel 能运行”当成正确性证明。

### 里程碑 A：Dart page table 描述层

1. 增加 `DartPageTable`，用 device tensor 保存 `page_id`、`sequence_start`、
   `token_count`、`key_mode`、`value_mode` 和 valid mask；
2. page table 从 `DartKVCache.iter_segments()` 构造，并在每次 append 后能重新
   构造或增量刷新；
3. 增加 `to(device)`、`validate()`、`reorder(batch_indices)` 和稳定的
   `sequence_ranges()`，对应 Kitty 的 page ID 与 batch/beam 生命周期，但不复制
   Kitty 的静态类名；
4. 用测试覆盖 sink/full/pending、跨 page append、空 cache、batch reorder、CPU/GPU
   device migration，以及 page table 与 `seen_tokens` 的一致性；
5. 先让 fused wrapper 使用 page table 的 tensor metadata 决定遍历范围，之后再把
   page id 作为 Triton kernel 的输入。

### 里程碑 B：多 page device-side loop

1. 为同一 storage mode 的连续 full pages 建立 page-major packed view，避免每页
   单独拼 Python 参数；
2. 增加 Triton page-run kernel，在一个 program 中循环 page id，跨 page 更新
   `m/l/o`，并支持最后一个不足 page 的 mask；
3. 先支持 uniform K/V，再支持 mixed key；dense sink 与 pending 作为边界 segment
   由同一状态接口处理；
4. 对随机 page 数、随机 page 长度、不同 group size 和 GQA 做 fused-vs-dense
   回归，确认 page 重排不会改变 token 顺序；
5. profile 必须同时报告 Python page launch 数、Triton page-run launch 数、状态
   临时显存和 kernel 误差。

### 里程碑 C：multi-query 与 adapter boundary

1. 将单 token kernel 的 `Q=1` 限制扩展为小 query tile，先支持 `Q=1/2/4`；
2. 为 attention adapter 定义只读 packed page 的接口，禁止隐式调用 `get()`；
3. 在 Qwen3 单层 hidden state 上比较 dense attention、PyTorch streaming 和

4. 只有单层 logits 逐元素/逐 token 稳定后，才尝试替换完整 Qwen3 attention，
