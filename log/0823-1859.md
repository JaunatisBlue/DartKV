## 参考 Kitty 后的工作安排修订

修订内容已经先写入并提交到 `log/0823-1804.md`，新增“本次用户确认后的修订
工作安排”。具体分为四个里程碑：

### A：Dart page table 描述层

- 用 device tensor 保存 batch-indexed `page_ids`、`sequence_starts`、
  `token_counts`、key/value mode 和 valid mask；
- 对应 Kitty 的静态 page ID 和 batch page table，但保留 Dart 动态 segment 存储；
- 提供 `to(device)`、`validate()`、`reorder(indices)`、`sequence_ranges()`；
- 覆盖 sink/full/pending、跨 page append、空 cache、batch reorder 和 device 迁移；
- 先由 fused wrapper 使用 metadata，后续再把 descriptor 直接交给 Triton page-run。

### B：多 page device-side loop

- 把同一 storage mode 的连续 full pages 组织成 page-major packed view；
- 在一个 Triton program 内循环 page id，跨 page 更新 `m/l/o`；
- 先支持 uniform K/V，再加入 mixed key；dense sink/pending 作为边界 segment；
- 分离 Python launch 数、page-run launch 数、状态显存和误差。

### C：multi-query 与 adapter boundary

- 将当前 `Q=1` kernel 扩展到 `Q=1/2/4` query tile；
- 设计不调用 `DartKVCache.get()` 的只读 packed attention adapter；
- 在 Qwen3 单层 hidden state 上比较 dense、PyTorch streaming 和 Triton fused logits；
- 单层 logits 稳定后，才尝试替换完整 Qwen3 attention。

### D：系统评测与 Kitty 对照

- 分离 quantize、page-run、state normalize、projection、模型 attention 和 tokenizer；
- 对照 Kitty 的 page size、K/V metadata layout、sink/local/Q-buffer 生命周期；
- 固定 Qwen3-8B、prompt suite、batch/beam、seed、dtype 和 backend；
- 单卡稳定后最后才安排双 A100 和多请求吞吐。

本次只执行 A，避免在 page ID 语义未冻结时同时改模型 attention 和多卡调度。

## Kitty 代码到 Dart 的对应关系

本次阅读并对照了以下 Kitty 文件：

- `reference/code/Kitty/src/kitty/kvcache/utils_kv_per_layer.py`：
  `PageTable_K/PageTable_V`、`PageCount_K/PageCount_V`、sink/Q-buffer/local buffer
  和总长度不变量；
- `reference/code/Kitty/src/kitty/kvcache/kitty.py`：prefill/decode 时 sink、page、
  Q-buffer 的生命周期切换；
- `reference/code/Kitty/src/kitty/kvcache/kernels/kitty_attention.py`：attention
  kernel 通过 page table 查 page id，并将 sink、paged page、Q-buffer、local value
  按逻辑顺序连接；
- `reference/code/Kitty/src/kitty/kvcache/kernels/kitty_quant_pack.py`：packed
  K/V 的 page-major 存储和 metadata stride。

Dart 本次没有复制 Kitty 的 `KVCache_Layer`、`PageTable_K` 命名或 CUDA/Triton
实现，而是把可验证行为映射为 `DartPageTable`：

| Kitty 行为 | Dart 本次实现 |
| --- | --- |
| `PageTable_K/V[B, MAX_PAGE]` | `DartPageTable.page_ids[B, N]` |
| page allocation id | 当前 segment index，后续再映射物理 packed page id |
| `PageCount_K/V` | `DartPageTable.page_count` |
| sink/page/Q-buffer 顺序 | `sequence_starts` + `token_counts` |
| key/value page layout | `key_modes` + `value_modes` |
| batch/beam row reorder | `DartPageTable.reorder(indices)` |
| `get_total_length()` invariant | `validate()` 检查 token counts 覆盖 `seen_tokens` |

当前 table 的 page ID 仍是逻辑 segment ID，packed tensor 仍由 `DartKVCache` 持有。
这一步有意没有伪装成 Kitty 的静态物理 allocator；下一步 page-run kernel 再把
逻辑 ID 映射到 page-major packed storage。

## 本次实现内容

### `src/dart/page_table.py`

新增 `DartPageTable` 和三个 mode 常量：

- `DENSE_PAGE = 0`；
- `QUANTIZED_PAGE = 1`；
- `MIXED_PAGE = 2`。

`DartPageTable.from_cache(cache)` 的构造过程：

1. 从 `cache.shape` 读取 batch 数，从 `cache.iter_segments()` 读取 page 对；
2. 检查 key/value 每个 segment 的 token 数一致；
3. 按 sequence 顺序生成 `starts`、`counts` 和 key/value mode；
4. 在目标 device 创建 int64 `page_ids[B,N]`，每一行初始为 `[0,1,...,N-1]`；
5. 创建 int32 `sequence_starts/token_counts`、int8 mode 和 bool valid tensor；
6. 检查累计 token 数等于 `cache.seen_tokens`。

`validate()` 不只检查 tensor shape，还检查：

- page start 是否由前一页 token count 连续生成；
- token count 是否正数、总和是否覆盖 cache length；
- mode 是否属于三个 Dart mode 常量；
- valid page ID 是否在 `[0, page_count)`；
- 空 cache 是否具有 `[0,0]` 的 batch/page 形状；
- page size 和 seen token 是否为合法范围。

`reorder(indices)` 只重排 `page_ids` 和 valid mask 的 batch 行，不复制 packed page
本体。这与 Kitty 的 batch-indexed page table 语义一致，也为后续 beam reorder
保留了独立的描述层。

### `DartKVCache.page_table()`

cache 新增：

```python
table = cache.page_table(device=query.device).validate()
```

空 cache、CPU cache、CUDA cache 和 cache `.to(device)` 后都可以重新构造 table。
page table 的生命周期由 cache append/reorder 驱动，不能在每个 decode token 内
无条件重建，因为创建 device tensor 和完整 validate 会产生额外同步。

### `fused_dart_attention(..., page_table=...)`

fused wrapper 新增可选的预构建 `page_table` 参数：

- 未传入时为兼容旧调用自动构造；
- 传入时检查 table device、page count、seen token 和每页 token count；
- kernel 仍然读取 cache segment 的 packed tensor，但遍历范围和长度由 table
  metadata 约束；
- 为下一步 page-run kernel 保留了无需重新解析 Python page descriptor 的入口。

profile 脚本在 cache update 后只构造一次并缓存 page table，额外记录
`page_table_build_ms`，避免把 page table 生命周期成本误算为 fused decode kernel
延迟。


新增 page table 测试包括：

- batch=2、sink=2、两个 full page、一个 pending page 的 page ID 和 range；
- dense/uniform/mixed key/value mode 检查；
- `reorder([1,1])` 的 batch row 语义；
- empty table 的 `[0,0]` 形状；
- append 后重新构造 table 的 page count 和 seen token；
- cache 转 CPU 后 page table 的 device 迁移。

已有 fused attention GPU 测试仍然把 `cache.get` 替换为抛错函数，证明新增
page-table 参数没有退回完整 materialize。

### A100 page table + fused profile

命令：

```bash
conda activate dartkv
python examples/profile_reference.py \
  --device cuda:0 --tokens 1024 --page-size 128 \
  --key-group-size 128 --value-group-size 64 --sink-tokens 32 \
  --kv-heads 8 --query-heads 32 --head-dim 128 \
  --promote-ratio 0.25 --repeats 3 --output results/profile-table
```

环境为 `cuda:0`、PyTorch 2.7.1+cu126、Triton 3.3.1、seed `20260823`，
`[B,Hkv,T,D]=[1,8,1024,128]`，`Hq=32`，page/key-group/value-group 为
`128/128/64`，32 sink，25% key promotion。结果如下，quantize 和 page table
build 各执行一次，其他 latency 为三次平均：

| 指标 | 结果 |
| --- | ---: |
| quantize + pack | 236.996 ms |
| page table build + validate | 42.611 ms |
| Triton segment dequantize | 1.104 ms |
| complete materialize | 3.475 ms |
| dense attention | 0.157 ms |
| Python page streaming | 137.057 ms |
| Triton fused page attention | 2.561 ms |
| fused page peak | 34,954,240 bytes |
| dense attention peak | 51,968,000 bytes |
| fused max abs/RMSE vs quantized dense | `1.53e-4` / `3.31e-5` |
| quantized dense max abs/RMSE vs original | `0.1151` / `0.03225` |
| Dart packed / dense storage | `1,133,568 / 4,194,304 bytes`（3.70×） |

这一轮 page table 构建约 42.6ms，明显不应放在每 token decode critical path；
profile 已经把它单独列出。fused page latency 受 GPU warmup、Triton cache 和
系统负载影响，本次为 2.561ms，与上一次同配置的 1.789ms 属于同一 kernel 路径，
不能用单次微小差异判断回归。正确性指标稳定，fused 仍比 Python page streaming
约快两个数量级以内，同时临时峰值低于 dense attention。

## 当前判断

### 已完成

1. 已先完善工作安排，再按安排完成里程碑 A 的第一版；
2. Kitty 的 batch-indexed page ID、page count、sequence range、mode 和 reorder
   语义已经映射到 Dart；
3. page table 有独立 device tensor、校验和测试，不依赖 Python list 才能判断长度；
4. fused wrapper 可以接受预构建 table，page table 生命周期成本已从 kernel latency
   中单独拆出；
5. 现有 22 个测试、Triton fused attention、Qwen adapter smoke 没有回归。

### 尚未完成

1. page ID 目前仍是 logical segment index，不是 Kitty 那种预分配物理 page slot；
2. Triton kernel 尚未直接读取 `page_ids/token_counts` 循环多个 page；
3. page table 的 `valid` 目前所有当前 page 都为 true，没有 free-list、capacity、
   partial-page slot 或跨请求 allocator；
4. batch reorder 目前只重排描述行，没有重排 cache 内部 packed tensor 的 batch 行；
5. Qwen3 模型仍未使用 fused attention，尚无单层 logits adapter 回归。
