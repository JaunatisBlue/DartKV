# DartKV 第三阶段完成记录与第四阶段建议

## 上一步工作概述

上一轮依据 `log/0823-1607.md` 完成了 Qwen3-8B 的本地 dense、uniform K2V2
和 mixed K2V2/K4 对照，以及 K/V 分离量化、动态 channel promotion、sink/page
buffer 和 `DartHFCache`。上一轮的模型 adapter 仍会在标准 Transformers
attention 前物化 dense K/V，因此它只能作为正确性和存储参考，不能作为 fused
attention 性能结果。

## 本轮完成内容

本轮把工作重点放在“流式 attention 的数值真值”和可复现实验入口，暂不直接
声称完成 Kitty 的 Triton/CUDA kernel：

### Page streaming reference

- `DartKVCache` 增加逻辑 `shape` 和按序 `iter_segments()`，可暴露完整 page 及
  pending partial page，而不复制完整 K/V；
- 新增 `dense_attention` 和 `streamed_dart_attention`。后者按 page 解量化，
  使用 float32 online softmax 累积器，并支持 query-head 到 KV-head 的 GQA 映射；
- streaming 路径不调用 `cache.get()`，因此可作为后续 fused kernel 的页面边界、
  量化布局、GQA 映射和生命周期 oracle；
- 增加回归测试，覆盖 mixed key、跨页、pending page 以及禁止完整 materialize
  的路径。

### Profiling 与评测入口

- 新增 `examples/profile_reference.py`，分别记录一次 `quantize + pack`、分段
  unpack/dequantize、完整 materialize、dense attention 和 page-streamed
  attention 的耗时与 CUDA 临时显存；可选导出 Chrome trace；
- 新增固定的一行一 prompt 文件 `examples/prompts.txt` 和
  `examples/run_qwen3_suite.py`。suite 记录每条 prompt 的生成、cache storage、
  峰值显存和 prefill/decode 数据，并复制配置字典，避免多 prompt 循环时记录被
  后续 prompt 覆盖；
- README 增加 page-streaming reference 的运行入口，详细结果写入中文文档
  `docs/PROFILE.md`。

### A100 合成 profiling

条件固定为 `cuda:0`、seed `20260823`、`[B,Hkv,T,D]=[1,8,1024,128]`、
`Hq=32`、page/key-group/value-group 为 `128/128/64`、32 个 sink token、25%
key channel promotion，延迟为重复 3 次的平均值（cache update 为一次操作）：

| 指标 | 结果 |
| --- | ---: |
| quantize + pack | 224.18 ms |
| 分段 unpack + dequantize | 0.517 ms |
| 完整 materialize（含 concat） | 0.565 ms |
| dense attention | 0.157 ms |
| page-streamed attention | 51.66 ms |
| streamed 对量化 dense 的 max abs/RMSE | `3.05e-5` / `5.52e-7` |
| 量化 dense 对原始 FP16 的 max abs/RMSE | `0.1272` / `0.03276` |
| Dart storage / dense storage | `1,127,424 / 4,194,304 bytes`（3.72×）|
| dense/streamed attention 临时峰值 | `51,934,208 / 43,713,024 bytes` |

streaming 比 dense 慢很多是预期结果：当前实现仍有 Python page loop、PyTorch
unpack 和每页临时张量。它证明了流式路径的结果和显存生命周期，不能把这个
Python reference 的延迟当作最终 kernel 性能。

## 当前未完成部分

1. 尚未实现 Triton/CUDA 的 low/high bit unpack、K/V 分离 dequant kernel 或
   fused attention；Qwen3 的 `DartHFCache` 仍使用 dense materialize adapter；
2. page metadata、channel index、scale/min 的最终 stride 和 page table 尚未冻结，
   目前只保证 PyTorch reference 的顺序和 pending 生命周期；
3. 尚未完成长上下文全量、多 batch/beam、多请求吞吐、双 A100 和完整 validation
   split；`lm-eval --limit 1` 仍只是 harness smoke check；

## 第四阶段工作安排

1. 先为 key/value page 写出固定 metadata/stride 规范和不变量测试，明确 sink、
   full page、pending page、channel index 的 token 顺序与 device 迁移行为；
2. 以当前 `streamed_dart_attention` 为真值，分别实现 value 和 key 的 Triton
   dequant/unpack 小 kernel，逐元素对照后再接入单 token online-softmax decode；
3. 在单卡正确性通过后，把 fused attention 接到模型层的最小 adapter，验证
   logits、greedy token、cache length、GQA 和 beam reorder，不保留完整 FP16 后备
   cache；
4. 扩展长上下文、多 prompt、多 batch/beam 的固定 harness，随后才做完整标准
   任务和多卡吞吐，统一记录有效样本、峰值显存、cache bytes、prefill/decode 和
   kernel 分项耗时；
5. 每个 kernel、模型 adapter、评测里程碑单独使用中文提交，继续保留 PyTorch
   reference 和原始 JSON/trace 作为回归依据。
