# DartKV 第四阶段续做：Kitty page-run 搬运与 fused attention 验证

## 上一步工作概述

上一份记录为 `log/0823-1859.md`。上一步已经完成 Dart page table 描述层：
`DartPageTable` 用 device tensor 保存 `[B,N]` page ID、page-major 的 sequence
range/token count、key/value mode 和 valid mask，并接入 `fused_dart_attention`。
当时的瓶颈仍然是 Python wrapper 对每个 page 单独发射 Triton kernel；因此本轮
按既定 B 里程碑继续，将连续 uniform full page 搬成 page-major run，并在一个
Triton program 内循环多个 page。

本轮目标是减少 kernel launch 次数，同时保持 Kitty 参考中的三个约束：逻辑 page
ID 与 storage 解耦、page 顺序可验证、online softmax 的 `m/l/o` 状态跨 page
连续更新。mixed key、dense sink 和 pending tail 先保留逐页边界路径，避免在布局
尚未稳定时扩大 kernel 分支。

## Kitty 对照与 Dart 映射

Kitty 的 `PageTable_K/V` 是 batch-indexed 的 page ID 表，kernel 通过 page ID
读取 page-major packed K/V 和 metadata；`PageCount` 与总长度不变量负责描述
生命周期。本轮 Dart 对应关系如下：

| Kitty 语义 | Dart 实现 |
| --- | --- |
| `PageTable_K/V[B, MAX_PAGE]` | `DartPageTable.page_ids[B, N]` |
| 静态物理 page id | 当前仍为 logical segment index |
| page-major packed fields | `DartPageRun` 第 0 维 stack |
| `PageCount` | `DartPageTable.page_count` / `DartPageRun.page_count` |
| page 长度与顺序 | `sequence_starts`、`token_counts`、`validate()` |
| sink/mixed/pending 边界 | 不进入 uniform run，继续逐页 kernel |

这不是 Kitty 代码的直接复制：Dart 仍使用 `DartKVCache` 的动态 segment 作为
owner，run 只是 kernel 消费用的 page-major view；后续接入物理 allocator 时，
只需替换 `page_indices` 到 packed storage 的映射，不必改变 attention 状态接口。

## 本轮实现

### 1. `DartPageRun` 生命周期

`src/dart/page_table.py` 新增 frozen dataclass `DartPageRun`，字段包括：

- `first_page_index` 与 `page_indices`：保留原 page table 的逻辑 ID；
- `sequence_starts`、`token_counts`：保证 run 内 page 仍按序列连续；
- `key_values/key_scale/key_zero_point`、`value_values/value_scale/value_zero_point`：
  沿第 0 维 stack 的 packed fields；
- key/value bits、group size 与 `page_size`：作为 kernel 的静态/运行时参数。

`DartPageTable.uniform_quantized_runs(cache)` 只合并满足以下条件的连续 segment：

1. key 和 value 都是 `QuantizedTensor`；
2. 每页长度恰好等于 `page_size`；
3. original shape、packed shape、metadata shape、bits 和 group size 一致。

因此 sink dense page、mixed key、pending tail 或布局变化都会自然切断 run。每个
run 在构造时执行 `validate()`，检查 page ID 连续、sequence range 连续、token
count 正数以及 page-major 第一维一致。run 提供 `to(device)`，便于把 descriptor
和 query 放到同一 CUDA device。

### 2. Triton uniform page-run kernel

`src/dart/fused_attention.py` 新增 `_fused_uniform_page_run_kernel`：每个
`(batch, query_head)` program 读取一个 query，在 `tl.range(0, page_count)` 中：

1. 按 page-major stride 解包 uniform key 的 token-axis bit pack；
2. 按 page-major stride 解包 uniform value 的 head-dim-axis bit pack；
3. 计算该 page 的 QK logits，并以 `m/l/o` online softmax 状态与前页合并；
4. 继续下一个 page，最终只写回一次 running max/sum/output。

wrapper 新增 `page_runs=` 参数：

- 未传入时从 page table 自动构造 uniform runs，保持旧 API 兼容；
- 传入预构建 runs 时校验 page ID、mode、范围，适合 decode loop 缓存；
- 传入 `page_runs=()` 可强制逐页 kernel，作为 launch/数值对照基线。

page-run 目前故意不包含 mixed key；当 run 以外的 page 出现时，wrapper 回到已有
的 dense/uniform/mixed 单页 kernel，因此 sink、mixed 和 pending 的逻辑顺序没有
改变。

### 3. profile 与文档

`examples/profile_reference.py` 现在分别记录：

- `page_table_build_ms`、`page_run_build_ms`、`page_run_count/page_run_pages`；
- `fused_page_attention_ms`（预构建 page-run）；
- `per_page_fused_attention_ms`（`page_runs=()` 强制逐页）；
- 两条路径各自的 peak memory。

`docs/PAGE_LAYOUT.md` 补充了 run 的 page-major 字段和调用示例；`docs/PROFILE.md`
与 `docs/EXPERIMENTS.md` 更新为本轮 uniform A100 profile，并明确 page-run build
属于 cache append 生命周期，不应算入稳定 token latency。

## 验证

### 自动化测试

```text
conda run --no-capture-output -n dartkv python -m pytest -q
24 passed in 6.89s

CUDA_VISIBLE_DEVICES=0 conda run --no-capture-output -n dartkv \
  python -m pytest -q tests/test_fused_attention.py
3 passed in 8.74s

python -m compileall -q src examples tests
通过
```

新增 CPU 回归覆盖：

- sink 后连续 uniform page 的 page-major stack shape、page ID 和 sequence range；
- mixed page 与 pending tail 不会被误合并；
- `DartPageRun.validate()` 的连续性检查。

新增/扩展 CUDA 回归覆盖：

- 35-token、sink=3、page=8、GQA=8/2 的 uniform page-run；
- page-run 与逐页 kernel 的输出对照，当前最大绝对差为 `0`（同一 Triton
  解码路径的状态更新顺序一致）；
- 原有 sink + mixed + pending + `cache.get` 禁用测试仍通过。

### A100 profile

命令：

```bash
CUDA_VISIBLE_DEVICES=0 conda run --no-capture-output -n dartkv \
  python examples/profile_reference.py --device cuda:0 --batch 1 --kv-heads 8 \
  --query-heads 32 --tokens 2048 --query-tokens 1 --head-dim 128 \
  --page-size 128 --key-group-size 128 --value-group-size 64 --sink-tokens 32 \
  --promote-ratio 0 --repeats 5 --output results/profile
```

得到：

| metric | value |
| --- | ---: |
| `page_table_build_ms` | `44.1170 ms` |
| `page_run_build_ms` | `1.0126 ms` |
| `page_run_count/page_run_pages` | `1 / 15` |
| dense attention | `0.2061 ms` |
| Python streamed attention | `320.5050 ms` |
| fused per-page | `4.4217 ms` |
| fused page-run | `2.3173 ms` |
| page-run peak | `61,845,504 B` |
| per-page peak | `61,845,504 B` |
| fused max abs / RMSE | `1.5259e-4 / 2.1475e-5` |

相对逐页 fused，page-run 延迟降低约 `47.6%`；相对 Python streaming 约快
`138×`。page-run 没有增加峰值显存，因为 stack 只保存 packed page 和 metadata，
attention state 仍为 `[B,Hq,D]`。该收益只说明 launch 合并方向有效，尚不能代表
完整模型吞吐；mixed page、Q tile、physical page allocator 仍是后续工作。

## 当前判断与下一步安排

本轮完成了 B 里程碑的 uniform 子集：page table 生命周期已能产出稳定的
page-major run，Triton 在一个 program 内跨 page 更新 softmax 状态，且与逐页路径
数值一致。当前仍有三项限制：

1. 每次未显式传 `page_runs` 时 wrapper 会重新 stack；生产 decode 应在 append 后
   缓存 table 和 runs，并在 reorder 时只更新 descriptor；
2. mixed key、dense sink、pending tail 仍逐页发射，page-run 收益随 mixed 比例
   上升而下降；
3. page ID 仍是逻辑 segment index，尚未接入 Kitty 式物理 page allocator 和
   batch-level indirection kernel。

下一步建议按以下顺序继续：

1. 为 `page_runs` 增加 cache-side 生命周期缓存/失效标记，避免 decode token 内
   重复 `torch.stack`；
2. 增加 mixed-key page-run（沿用 low/high/index 三组 stride），并把 dense sink
   与 pending tail 作为显式边界 run；
3. 扩展 Q=1 tile 到 Q=2/4，减少 query-head program 数，重新 profile launch
   和峰值显存；
4. 设计逻辑 page ID 到物理 packed page 的独立映射，再对照 Kitty 的 batch/beam
   reorder 与多请求调度；
5. 在单层 Qwen3 attention 中接入只读 packed adapter，完成 logits 数值回归后再
   讨论完整模型替换。
