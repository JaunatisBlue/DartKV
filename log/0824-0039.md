## 本周期完成内容

### 1. Figure 5 同协议长上下文结果

固定 Kitty `prompt_choice=1`、Qwen3 chat template、FP16、A100、`batch=1`、总长度 8192、
warmup 1、repeat 1，实际生成 7013 tokens：

| cache | elapsed | throughput | peak memory | KV storage | storage ratio |
| --- | ---: | ---: | ---: | ---: | ---: |
| FlashAttention dense | 323.81 s | 21.66 tok/s | 17.62 GB | 1.208 GB | 1.00x |
| Kitty official Triton engine | 414.49 s | 16.92 tok/s | 17.04 GB | 224.2 MB | 5.39x |

两条路径的首段 token ID 一致；当前长序列 engine/dense 吞吐比约 `0.781`。这证明
FlashAttention 安装和 Kitty engine 都能实际工作，但也明确表明本机当前 Triton/自定义
attention 路径还没有达到论文宣称的 2.1–4.1x 系统加速，不能把该结果写成“已复现”。

### 2. 中等 batch 对照

固定总长度 2048、`batch=4`、其余协议不变，生成 3476 tokens：

- FlashAttention dense：41.46 s，83.84 tok/s，峰值 17.62 GB；
- Kitty engine：51.60 s，67.37 tok/s，峰值 18.43 GB；
- 吞吐比约 `0.804`。由于 Kitty 的静态 page/Q/Local buffer 在短长度有固定开销，
  此时 storage ratio 只有 0.934x；这与 8192 长度的 5.39x 压缩并不矛盾。

## 当前判断

环境安装问题已经闭合，性能问题仍未闭合。Kitty engine 的显存占用和长上下文 KV 压缩已
达到预期方向，但吞吐低于 FA2 dense；这更可能来自 Triton kernel launch/page 解码路径和
当前 PyTorch/Triton 版本差异，而不是 FlashAttention 缺失。必须进一步做 batch-until-OOM
和 kernel profile，才能判断是软件环境差异还是搬运实现瓶颈。
