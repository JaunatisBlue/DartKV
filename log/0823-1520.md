# DartKV 第二阶段工作指导

## 上一步工作概述

第一阶段已经完成 DartKV 的基础工程和可运行性验证，提交记录为 `e7b5b9c init dart pytorch kv cache baseline`。主要成果如下：

- 建立了独立的 `dart` Python 包，没有复用 Kitty 的包名、类名或命令名；
- 实现了设备无关的 PyTorch 参考量化器，支持 2/4/8-bit 非对称分组量化、bit packing、反量化和非整除维度；
- 实现了使用 `[batch, kv_heads, sequence, head_dim]` 布局的增量式 `DartKVCache`，支持全精度 sink token、存储统计和 CPU/GPU 迁移；
- 提供了命令行冒烟测试和固定随机种子的合成 attention baseline；
- 建立了 `pyproject.toml`、依赖文件、环境快照、README、来源说明、MIT 许可证和 `.gitignore`；
- 在 `dartkv` conda 环境中验证了 Python 3.10.20、PyTorch 2.7.1+cu126、CUDA 12.6，以及两张 NVIDIA A100 80GB PCIe；
- 单元测试和 GPU 测试共 9 项全部通过，`pip check` 没有发现依赖冲突；
- 默认合成配置 `[1, 8, 256, 128]`、2-bit、group size 64、32 个 sink token 的存储压缩比约为 3.82 倍，attention 输出 RMSE 约为 0.0665。

第一阶段证明了环境、基本数据结构和数值路径可用，但这些结果不能直接解释为论文复现或性能收益。当前代码仍有以下边界：

1. 尚未接入 Hugging Face 模型和真实 tokenizer，不能运行实际文本生成或任务准确率评测；
2. 当前 key 和 value 都沿最后一维量化，而参考方法通常需要分别处理 key 的通道/时间维和 value 的 token/通道维；
3. 尚未实现 Dart 的动态通道选择和 2/4-bit 混合精度提升策略；
4. 当前 attention baseline 会先完整反量化 K/V，再调用 PyTorch attention，因此只适合检查数值误差；其耗时不能用于证明量化 cache 加速或降低 attention 峰值显存；
5. 尚未实现分页存储、decode buffer、真实模型 cache adapter、任务评测及严格的 dense/quantized 对照实验；
6. `/opt/model` 中目前没有发现可直接使用的模型配置，开始真实模型实验前需要下载并记录模型来源、revision 和许可证。

## 对下一阶段的判断与建议

第二阶段应优先解决“算法语义和真实模型正确性”，暂时不直接进入 Triton/CUDA kernel 优化。如果模型集成、量化轴和准确率尚未稳定，提前实现 kernel 会放大排错范围，也无法判断性能提升是否建立在正确结果上。

建议把 Kitty 当作可比较的参考实现，而不是 DartKV 的目标架构。下一阶段需要从其 Qwen3 接入、K/V 量化方式、sink/page/buffer 生命周期和评测协议中提取可验证行为，同时继续保持 DartKV 自己的配置、接口和模块命名。若没有直接复制 Kitty 的实质代码，只需在文档中说明设计来源和论文引用；若后续改编了其 MIT 代码的实质部分，则必须在相关文件或发行物中保留其版权和许可声明。

## 第二阶段目标与工作范围

第二阶段的核心目标是：在真实 Qwen3 模型(/opt/model/Qwen/Qwen-8B)上完成 FP16、均匀低比特和 Dart 混合精度 KV cache 的可复现对照，并使结果足以支持后续 kernel 优化。交付物包括：

- 一个基于标准 Hugging Face 接口的模型加载与生成入口；
- 一个与模型 cache 生命周期兼容的 Dart cache adapter，支持 prefill 和逐 token decode；
- 分离的 key/value 量化配置和正确的量化轴；
- Dart 的动态 key 通道评分、选择和低/高比特混合精度参考实现；
- FP16、均匀 2-bit 和 Dart 混合精度三组对照实验；
- 数值误差、生成一致性、任务质量、KV 存储、峰值显存、prefill 和 decode 延迟记录；
- 对模型、数据、依赖、命令、配置和原始结果的完整记录；
- 为第三阶段的 Triton/CUDA 优化给出经过 profiling 支持的接口和热点结论。

本阶段不要求复现论文的全部模型、全部任务和最终 kernel 性能，也不要求默认使用双卡。先在单张 A100 上完成 Qwen3-4B 的正确性和小规模评测；只有模型容量或明确实验需要时才使用第二张 GPU。

## 模型与环境安排

1. 所有操作必须在 `dartkv` conda 环境中进行。开始前重新运行环境检查和现有测试，确保第一阶段基线没有回归。
2. 在现有锁定依赖上增量安装模型接入所需的最小依赖。优先考虑官方稳定版 `transformers`、`safetensors` 和 tokenizer 依赖；仅在确实使用 `device_map` 时加入 `accelerate`。暂不安装 flash-attn、HQQ 或自定义 lm-eval 分支。
3. 优先选择 Kitty 明确支持的 `Qwen/Qwen3-8B`(存放于/opt/model/Qwen/Qwen-8B) 作为第一个真实模型。
4. 下载或安装遇到网络问题时，可以按需使用 `http://127.0.0.1:14568` 代理；代理只用于当前命令或明确的环境变量，不要把凭据或机器私有配置写入仓库。
5. 将新增的顶层依赖写入 `requirements.txt`，验证后更新完整锁定文件和 `docs/ENVIRONMENT.md`。模型 revision、dtype、attention backend 和 tokenizer 版本必须进入实验元数据。
6. 第一条真实模型链路使用单卡 FP16/BF16 和 eager/SDPA 中兼容性最稳定的实现。不要一开始混入量化 cache、双卡、`torch.compile` 和 flash-attn；先证明标准 dense cache 可以确定性生成。

## 算法与接口设计

1. 将通用量化器扩展为显式支持量化轴或在外部完成可靠的维度变换，不能用“最后一维量化”隐式代替 K/V 的不同语义：
   - key cache 参考按通道沿 token/page 维分组，以保留 key 的通道结构；
   - value cache 参考按 token 沿 `head_dim` 分组；
   - padding、scale/min、bit packing 和反量化后的布局必须有独立测试。
2. 将配置拆分为 `key_bits`、`value_bits`、`key_group_size`、`value_group_size`、`sink_tokens`、`page_size`、`promote_bits`、`promote_ratio` 和 `channel_selection` 等明确字段，避免一个参数同时控制不同语义。
3. 实现 Dart 的动态 key 通道选择参考路径，至少支持 magnitude 和 variance 两种评分，并允许关闭 promotion 形成均匀 2-bit 对照。选择结果应可检查，固定输入和随机种子时必须可复现。
4. promotion 应真实改变存储表示：普通通道使用 2-bit，选中通道使用 4-bit，同时准确计入低位数据、高位数据、索引和量化元数据；不能只做 fake quantization 后仍以 FP16 保存。
5. 建立清晰的 cache 生命周期：全精度 sink、待量化 buffer、量化 page 和必要的 local window 分开管理。prefill 和 decode 更新应共享同一套长度、不重不漏地恢复原 token 顺序。
6. 优先通过 Transformers 公共 `Cache` 接口或小型 adapter 接入模型，不要复制整个 Qwen3 `modeling_*.py`。如果上游接口不足而必须修改模型代码，应把适配层隔离在 `src/dart/integrations/`，记录所依赖的 Transformers 版本和最小改动原因。
7. 保留纯 PyTorch reference path 作为数值真值。任何未来 kernel 都必须与该路径在相同输入、布局和配置下比较，而不是以 kernel 自身结果作为正确性依据。

## 实现与实验顺序

**建议参考kitty源码进行实现，同时更要结合最新通用推理代码进行**

### 里程碑一：真实模型 FP16 基线

1. 模型已经存放在/opt/model/Qwen/Qwen-8B
2. 建立模型加载、prompt tokenization、greedy generation 和结果保存入口；
3. 固定 prompt、seed、dtype、最大输入/输出长度和 attention backend；
4. 在单张 A100 上记录加载显存、prefill 峰值显存、逐 token decode 延迟和生成文本；
5. 增加最小模型集成测试，但默认测试不能要求重新下载模型。
6. 实验数据要有记录，建议存放在一个单独的文件夹。
### 里程碑二：Dart 量化语义与混合精度

1. 先完成 K/V 分离量化轴和均匀 2-bit cache，并与独立 fake-quant 路径做数值对照；
2. 再实现 magnitude/variance 通道评分及 2/4-bit promotion；
3. 增加 page、sink、短序列、跨页 decode、非整除维度、不同 dtype/device 和非法配置测试；
4. 检查实际打包数据与理论 bit budget，明确元数据和索引开销；
5. 在合成 attention baseline 上比较 FP16、K2V2 和 Dart mixed-precision 的输出误差。

### 里程碑三：Hugging Face cache 接入

1. 将量化 cache 接入 Qwen3 的 prefill 和 autoregressive decode；
2. 在关闭量化或使用高精度配置时，与 Hugging Face dense cache 检查 logits 和 greedy token 序列；
3. 在均匀 2-bit 和 Dart mixed-precision 下验证 cache 长度、位置编码、batch/head 布局和生成终止行为；
4. 不允许通过忽略 cache、每步重新 prefill 或完整保存一份隐藏 FP16 K/V 来伪造兼容性；
5. 只有正确性测试通过后，才记录实际生成的显存和延迟数据。

### 里程碑四：小规模质量与性能评测

1. 至少完成 FP16、均匀 K2V2、Dart 2/4-bit promotion 三组配置；
2. 首先使用固定 prompt 集检查生成和长上下文稳定性，再选择一个无需私有分支、协议明确的标准任务做小规模评测；
3. 若使用 lm-evaluation-harness，应固定官方版本和任务配置，不直接依赖 Kitty 的私有分支，建议使用lm-evaluation-harness；
4. 记录任务指标、有效样本数、失败样本、随机种子和原始输出，不能只保留汇总分数；
5. 分别测量 prefill、decode、cache 更新、反量化/attention 以及端到端生成。进行 warmup、同步 CUDA，并报告均值、离散程度和重复次数；
6. 同时报告逻辑 KV 大小、实际 tensor 存储、`torch.cuda.max_memory_allocated()` 和模型总峰值显存，避免把理论 bit 数当作真实显存收益；
7. 使用 profiler 定位主要开销，并据此决定第三阶段先优化量化 packing、反量化 attention 还是 cache 调度。

## 验收标准

第二阶段完成需要同时满足以下条件：

- 从文档可以在 `dartkv` 环境中安装依赖、定位 `/opt/model` 权重并运行同一条模型命令；
- Qwen3-8B 的 dense FP16/BF16 baseline 能在单张 A100 上完成固定 prompt 的 greedy generation；
- K/V 量化轴、分组、packing、promotion、page/sink/buffer 生命周期均有独立测试；
- CPU 单元测试全部通过，GPU 测试和至少一个真实模型集成测试通过；
- FP16、均匀 K2V2 和 Dart mixed-precision 三组实验使用相同模型、prompt/数据、生成参数和评价协议；
- 结果包含准确率或生成质量、数值误差、实际 KV 存储、峰值显存以及 prefill/decode 延迟，而不是只报告压缩比；
- Dart 模式在生成过程中确实使用量化 cache，不保留等价的完整 FP16 K/V 后备副本；
- 所有模型、数据、revision、依赖、命令、配置和结果目录都有记录，实验能够从固定 seed 重复；
- README、环境文档、参考来源和已知限制已同步更新；
- `git diff --check`、测试和 `pip check` 通过，工作区没有权重、数据、缓存、密钥或构建产物。

## 提交与后续记录规则

按里程碑提交，而不是把模型接入、算法修改和评测脚本混在一个大提交中。建议提交顺序为：

1. `add qwen3 dense generation baseline`；
2. `separate dart key value quantization`；
3. `add dart mixed precision channel promotion`；
4. `integrate dart cache with qwen3 decoding`；
5. `add reproducible dart evaluation suite`。

每次提交前运行与改动范围相匹配的测试并检查 staged diff。不要提交 `/opt/model` 中的模型、下载缓存、原始数据集、实验临时文件或 Hugging Face token。完成第二阶段后，在 `log/` 下按时间命名新增一份记录，概述实际完成内容、没有达到的部分、关键实验结果、问题判断和第三阶段工作建议。
