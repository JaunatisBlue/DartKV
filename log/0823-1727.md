# DartKV 第四阶段进行记录与第五阶段建议

## 上一步工作概述

第三阶段依据 `log/0823-1607.md` 完成了按 page 逐段解量化的 PyTorch
`streamed_dart_attention`、online softmax、GQA head 映射、固定 prompt suite 和
合成 profiling。第三阶段保留了 PyTorch 路径作为数值真值，但还没有冻结 packed
page 的 metadata/stride，也没有把解量化接入 Triton/CUDA kernel。

## 本轮完成内容

### Page 边界与 metadata

- 修正 `DartKVCache._quantize_pages`：一次 update 含多个完整 page 时，现在严格
  逐 page 生成 quantized segment，不再把多个 page 错误地合并到同一个对象；
- 新增 `DartPageMetadata` 和 `DartSegmentLayout`，通过
  `cache.page_metadata()` 固定 segment 的 sequence 起点、token 数、逻辑 shape、
  packed 字段 shape 和 element stride；
- 增加 key/value segment 数量、pending key/value、page token 数和总长度不变量
  检查；
- 在中文文档 [`docs/PAGE_LAYOUT.md`](../docs/PAGE_LAYOUT.md) 中记录 sink、full
  page、pending page、uniform/mixed key、uniform value 的字段和 stride 约定。

### 可选 Triton 解包 reference

- 新增 `src/dart/triton_ops.py`，提供 uniform value（最后一维）、uniform key
  （token 轴）和 mixed key（低 2-bit + promoted 高 2-bit）的 Triton 解包/仿射
  反量化小 kernel；
- `triton_dequantize` 在 CUDA 且 Triton 可用时走 kernel，否则自动回退到 PyTorch
  reference，避免 CPU 单元测试依赖 GPU；
- `streamed_dart_attention` 已调用该接口，但 QK、online softmax 和 SV 仍未融合，
  所以当前多 page、多 head 下的 kernel launch 次数较多；
- 增加 CPU fallback、uniform/mixed GPU 对照测试，允许 FP16 affine expression
  的 `atol=4e-3` 舍入差异。

## 验证结果

### 自动化与 GPU kernel

- `conda run --no-capture-output -n dartkv python -m pytest -q`：`18 passed`；
- `compileall`、`pip check`、`git diff --check` 均通过；
- 在 `cuda:0` 上测试 2/4/8-bit uniform key/value、mixed key、非整除 token/page、
  `promote_ratio=0` 和无 promoted channel，Triton 结果与 PyTorch reference 对齐；
- Triton 版本为 `3.3.1`，CUDA runtime 为 `12.6`。

### A100 page-streaming profile

条件为 `cuda:0`、seed `20260823`、`[B,Hkv,T,D]=[1,8,1024,128]`、`Hq=32`、
page/key-group/value-group 为 `128/128/64`、32 sink token、25% promotion、重复
3 次。第四轮已按真实 page 边界拆分，并使用 Triton dequantization：

| 指标 | 结果 |
| --- | ---: |
| quantize + pack | 232.89 ms |
| 分段 Triton unpack + dequantize | 1.11 ms |
| 完整 materialize（含 concat） | 3.39 ms |
| dense attention | 0.151 ms |
| page-streamed attention | 136.28 ms |
| streamed 对量化 dense 的 max abs/RMSE | `1.83e-4` / `3.59e-5` |
| quantized 对原始 attention 的 max abs/RMSE | `0.1151` / `0.03225` |
| Dart packed / dense storage | `1,133,568 / 4,194,304 bytes`（3.70×） |
| streamed 临时峰值 | `35,510,784 bytes` |

streaming 延迟显著高于 dense 是预期的：当前仍然按 query head、page 单独发射
Triton 解包，并在 Python 中执行 QK、online softmax 和 SV。这个结果只能证明
布局、数值和显存生命周期，不能作为 kernel 加速结论。

### Qwen3 cache adapter smoke

使用 `/opt/model/Qwen/Qwen3-0.6B`、BF16、eager、seed `20260823`、prompt
`Define a KV cache in one sentence.`、8 input tokens 和 3 new tokens：dense 与
Dart mixed（sink 2、page 8、key/value group 8、25% promotion）都生成
`A KV cache`。Dart storage 为 `616,448` bytes，dense 对照为 `1,146,880` bytes，
压缩比 `1.86×`。该 adapter 仍会在标准模型 attention 前物化 K/V。

## 当前未完成部分

1. 尚未把 Triton 解包、QK、online softmax、SV 融合为单一 attention kernel；
2. `DartHFCache` 尚未绕过 Transformers 标准 attention 的 dense K/V 接口，模型
   端仍然不是 fused-memory decode；
3. page allocator、跨请求 page table、并发 batch、beam reorder 的 packed 原地
   路径，以及多卡吞吐尚未实现；
4. 尚未完成长上下文完整 validation split 和统一的 dense/uniform/mixed 质量评测。

## 第五阶段建议

1. 先实现单 token、单 page 的 Triton online-softmax attention，分别验证 QK 和
   SV，再扩展到 sink、pending 和多 page；
2. 为 `DartHFCache` 增加明确的 fused-attention adapter 边界，禁止隐式调用
   `get()`，并用 logits/token 与当前 dense adapter 做逐层回归；
3. 冻结 page table 和 batch/beam reorder 语义后，再做长上下文、多 batch、beam
   和请求混合的 benchmark；
4. 只有在单卡 kernel 与模型正确性稳定后，才进行双 A100 切分或吞吐评测；每个
   kernel、adapter 和评测里程碑继续单独使用中文提交。
