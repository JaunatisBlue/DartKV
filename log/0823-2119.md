# DartKV 第四阶段续做：缓存 page table/page-run 生命周期

## 上一步工作概述

上一份记录为 `log/0823-1952.md`。上一步已经完成 Kitty 风格 page table 到 Dart
的 page-run 搬运：连续 uniform full page 的 packed K/V 与 metadata 按 page-major
stack，并在一个 Triton program 内循环 page、跨页更新 online softmax 的 `m/l/o`。
uniform 配置下 15 个 page 合并为一个 run，fused 延迟从逐页的约 `4.42 ms` 降到
`2.32 ms`；mixed key、dense sink 和 pending tail 仍走逐页 kernel。

上一步记录的下一项工作是“为 `page_runs` 增加 cache-side 生命周期缓存/失效标记”，
避免 decode token 内重复 `torch.stack`。本次继续执行这一项，并同时补齐 append、
clear、device 迁移和 HuggingFace beam reorder 的描述生命周期测试。

## 本轮目标与设计判断

page table 和 page-run 都是 cache layout 的派生描述，不应成为每个 decode token 的
Python 构建成本。Kitty 中 page table 随 page allocation 和 beam 状态变化；Dart
没有直接复制 Kitty 的物理 allocator，而是把同样的生命周期边界映射为：

| 事件 | Dart 描述动作 |
| --- | --- |
| cache append | 新 segment/pending tail 形成后递增 layout version，失效 table/run |
| `clear()` | 清空 storage 后递增 version，生成新的 `[0,0]` table |
| `to(device)` | packed storage 搬迁后递增 version，丢弃旧 device descriptor |
| beam reorder | HF adapter 重建选中 layer，旧 layer descriptor 不再复用 |
| decode token | 只读取同 version、同 device 的缓存 descriptor |

保留 `rebuild=True` 作为调试/一致性检查入口；正常路径使用默认缓存。缓存 key 是
canonical `torch.device`，因此 CPU、`cuda:0` 等不同 descriptor placement 互不混用。

## 实现内容

### 1. `DartKVCache` layout version 与 descriptor cache

`src/dart/cache.py` 新增：

- `layout_version` 只读属性；初始化为 0，每次成功 append、`clear()` 或 `to(device)`
  递增；
- `_page_table_cache`：`device -> (layout_version, DartPageTable)`；
- `_page_run_cache`：`device -> (layout_version, tuple[DartPageRun, ...])`；
- `_invalidate_page_descriptors()` 统一清空两个缓存。

`cache.page_table(device=None, rebuild=False)` 的行为：

1. 默认 device 为当前 cache storage device；空 cache 默认 CPU；
2. 同一 version/device 直接返回原 descriptor 对象；
3. append/clear/to 后旧字典被清空，下一次调用重新从 `iter_segments()` 生成；
4. `rebuild=True` 强制创建新对象，但不会改变逻辑 layout version。

`cache.page_runs(device=None, page_table=None, rebuild=False)` 同样按 device 缓存
uniform page-run。未传自定义 table 时可直接复用；传入 reorder 或调试 table 时只
构建临时 runs，不覆盖 cache-owned entry。若显式 device 与 packed storage 不同，
run 的所有 packed fields 会一次性迁移到目标 device，避免 kernel 内隐式逐字段搬运。

### 2. fused attention 与 profile 接入

`fused_dart_attention` 在未显式传 `page_table/page_runs` 时，现在调用
`cache.page_table(device=query.device)` 和 `cache.page_runs(device=query.device)`；
因此默认 decode 调用不会每次重新执行 `torch.stack`。显式传入 page table 仍按调用
者意图使用，显式 `page_runs=()` 仍可强制逐页基线。

`examples/profile_reference.py` 除首次构建耗时外新增：

- `page_table_cached_lookup_ms`；
- `page_run_cached_lookup_ms`。

这两个数字只测同一 cache version/device 的命中路径，和首次构建分开记录，避免把
生命周期成本误算为 token kernel latency。

### 3. HuggingFace adapter 边界

`DartHFCache` 新增 `page_table(layer_idx)` 与 `page_runs(layer_idx)` 透传接口，
供 fused attention caller 读取指定 layer 的 Dart descriptor。现有
`reorder_cache(beam_idx)` 仍按 adapter 的 correctness-first 约定重建选中 beam 的
layer cache；重建后得到新的 underlying `DartKVCache`，因此旧 table/run 不会跨
beam 生命周期复用。

## 验证结果

### 自动化测试

```text
python -m pytest -q tests/test_cache.py tests/test_fused_attention.py
16 passed in 7.02s

python -m compileall -q src examples tests
通过

python -m pytest -q
27 passed in 7.00s
```

新增回归包括：

- 相同 version/device 下 table 与 run 对象 identity 保持不变；
- append 后 page count 增长且旧 table/run 被替换；
- `rebuild=True` 只创建新对象，不改 version；
- `to("cpu")` 和 `clear()` 使旧 device descriptor 失效；
- 自定义 reorder table 的临时 run 不覆盖 cache-owned run；
- `DartHFCache.reorder_cache()` 后通过公开 `page_table()` 获得新 layer descriptor。

### A100 生命周期 profile

命令：

```bash
CUDA_VISIBLE_DEVICES=0 conda run --no-capture-output -n dartkv \
  python examples/profile_reference.py --device cuda:0 --batch 1 --kv-heads 8 \
  --query-heads 32 --tokens 2048 --query-tokens 1 --head-dim 128 \
  --page-size 128 --key-group-size 128 --value-group-size 64 --sink-tokens 32 \
  --promote-ratio 0 --repeats 3 --output results/profile
```

固定 seed `20260823`、A100 `cuda:0` 的关键结果：

| metric | value |
| --- | ---: |
| first `page_table_build_ms` | `52.5282 ms` |
| cached table lookup | `0.01049 ms` |
| first `page_run_build_ms` | `0.8898 ms` |
| cached run lookup | `0.00436 ms` |
| page run count/pages | `1 / 15` |
| fused page-run | `2.3195 ms` |
| forced per-page fused | `4.3927 ms` |
| fused max abs / RMSE | `1.5259e-4 / 2.1475e-5` |

缓存命中相对首次 table 构建约减少三个数量级，相对首次 run stack 也约减少两个
数量级；这验证了把 descriptor 放进 cache 生命周期的必要性。attention 数值和
上一步一致，page-run 与逐页 kernel 的状态更新仍然保持同一误差范围。

## 当前限制与下一步安排

本轮解决了 uniform run 的 Python stack 重复问题，但仍有以下边界：

1. `DartPageRun` 只支持连续 uniform quantized K/V；mixed key 仍不能合并；
2. HF adapter 的 beam reorder 仍重建 dense K/V 后重新量化，尚未做到 Kitty 式物理
   page ID 行重排；
3. fused kernel 仍是每个 `(batch, query_head)` 一个 program，Q=2/4 tile 尚未加入；
4. page ID 仍是 logical segment index，尚未接入真正的 physical allocator。

建议下一轮顺序：

1. 为 mixed key 增加 low/high/index page-run，先覆盖同一 promotion layout；
2. 将 sink、pending 组织为显式边界 descriptor，减少逐页 wrapper 分支；
3. 扩展 Q=1 到 Q=2/4 query tile，profile launch 数、状态显存和误差；
4. 在 HF adapter 中探索只重排 page table row 的 beam path，避免重建 dense K/V；
5. 冻结逻辑 ID 到 physical packed page 的 indirection 后，再讨论多请求调度。

pytest、compileall、`pip check` 与 `git diff --check`。
