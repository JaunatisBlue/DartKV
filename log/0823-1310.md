# DartKV 第一阶段工作指导



### 目标与工作范围

工作目录固定为 `/home/yx/DartKV`。请参考 `/home/yx/DartKV/reference/code` 下的实现，并结合 `reference/paper` 中与 KV cache 压缩/量化相关的论文，搭建 DartKV 的第一版基础代码。第一阶段的交付物是：

- 一个独立的 `dart` Python 包及清晰的模块边界；
- 能在本机 GPU 上运行的最小 KV cache 量化/压缩流程（先提供 PyTorch 参考实现）；
- 一个可复现的 baseline，明确模型、输入、量化配置、指标和运行命令；
- 安装说明、环境版本记录、冒烟测试和数值正确性测试；
- 一份记录参考来源、实现差异、已知限制和下一步计划的文档。

暂不要求第一阶段完成全部论文实验、生产级 kernel 或自动双卡调度。若后续需要，可在基线验收后单独安排性能和扩展工作。

### 环境建立与验证

1. 使用现有的 conda，并确保工作在名为 `dartkv` 的环境中，Python 版本为 3.10。若该环境不存在才创建；不要把依赖安装到 `base` 环境，也不要覆盖用户已有的环境。
2. 开始前检查并记录以下信息：
   - `python --version`、`which python`、`conda env list`；
   - `nvidia-smi` 的 GPU 型号、显存、驱动版本和数量；
   - `torch.cuda.is_available()`、`torch.version.cuda`、`torch.cuda.device_count()`。
3. 根据主机驱动和 Python 版本选择相互兼容的 PyTorch、Transformers 及其他依赖。Kitty 的 CUDA 12.1 容器只能作为兼容性参考，不能直接照搬其过旧的环境版本；优先使用官方 wheel/conda 包。
4. 只安装当前实现确实需要的依赖。`flash-attn`、Triton、HQQ、`optimum-quanto` 等属于可选或可能需要编译的组件，先完成无它们的参考实现；确认必要性、版本兼容性和收益后再安装。
5. 将最终环境写入 `environment.yml`、`requirements.txt` 或等价的锁定文件，并在文档中注明安装日期、CUDA/PyTorch 版本和已验证的 GPU。安装后先执行导入检查和一个小张量 GPU 运算，失败时先修复环境，不要继续堆叠依赖。
6. 对于环境安装我们希望你合理使用conda和pip，如果遇到网络问题可以考虑代理： http://127.0.0.1:14568
7. 一些需要系统去安装的工具比如nvcc等，如有需要可以安装。注意我的os版本是ID="rocky",ID_LIKE="rhel centos fedora",VERSION_ID="10.1,你需要从nvidia的官网找到适配。
8. 需要用hf下载模型的话，用/opt/model/文件夹
### 参考代码与命名规范

- 先阅读 Kitty 的 README、`pyproject.toml`、许可证、KV cache、量化、评测和 kernel 相关代码，整理出可复用的设计和需要避开的旧环境假设。
- 参考实现中的 `kitty` 包名、类名、CLI 名称和文件命名不要直接复用；DartKV 的公开 API、目录和命令统一使用 `dart`/`dartkv` 命名。
- 不要复制与当前目标无关的大段代码。当前 Kitty 仓库附带 MIT 许可证；确需改编时，保留许可证要求的版权/来源信息，并在 DartKV 文档中注明原文件、改动点和行为差异；不要依赖未安装的 Kitty 子模块或其私有分支。
- 论文中的算法描述、参考代码中的工程实现和 DartKV 的新设计要分别记录，避免把参考实现的假设误当成论文结论。
- kitty中的readme展现了引用论文的规范，但是对于mit标准等暂无？你需要判断。

### 实现顺序

1. 盘点参考代码和论文，确定第一版支持的模型接口、KV cache 张量布局、量化粒度、位宽、校准方式、解码路径和评价指标；把未确定的选择写入配置或 TODO。
2. 在 `src/dart`（或等价的包目录）实现最小、可读的 PyTorch 版本，并提供 CPU/单 GPU 的明确设备选择。先用合成张量或很小的公开模型验证形状、反量化误差、缓存读写和生成流程。
3. 增加独立的单元测试和 GPU 冒烟测试，覆盖边界形状、不同序列长度、非整除分组、异常配置及 dtype/device 转换。
4. 选定一个 baseline 进行小规模复现，固定随机种子和配置，记录吞吐/延迟、显存、量化误差及任务准确率。结果与参考实现不一致时，先定位模型版本、数据、tokenizer、精度和评测脚本差异。
5. 基线通过后，再按 profiling 结果选择性加入 kernel、flash-attn、混合精度或双 A100 支持。双卡不是默认前提：先保证单卡结果正确，再验证多卡的收益、通信开销和可复现性。
6. 完成任务后，把下一步的工作计划、建议以及你的思考写入log/下，注意命名格式
### 验收与提交规则

每个里程碑都应满足以下条件后再进入下一步：

- 按文档从干净的 `dartkv` 环境安装并完成导入检查；
- 冒烟测试和数值测试通过，GPU 不可用时能给出清晰错误或安全地运行 CPU 测试；
- baseline 命令、配置、版本和结果位置明确，不能依赖未记录的 shell 状态；
- `git status` 和 `git diff` 已检查，没有把权重、数据、缓存、密钥或临时构建文件加入版本库。

完成一个逻辑完整的修改后再执行 `git add` 和 `git commit`，提交信息应说明阶段性目的（例如 `init dart pytorch baseline`）。不要为了“定期提交”而提交无法运行的半成品，也不要使用强制重置覆盖已有工作。

遇到环境、论文解释或参考代码行为存在歧义时，先保留可复现的诊断信息，说明假设、证据和影响，再选择最小风险的方案继续；不要默默改变模型、数据或评价协议。
